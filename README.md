# RaceSide

Веб-приложение для русскоязычных болельщиков Формулы-1: новости, гоночный уикенд, LIVE, телеметрия и прогнозы в одном месте.

**Сайт:** [raceside.online](https://raceside.online) · **Бот:** [@raceside_bot](https://t.me/raceside_bot)

## Возможности

- Новости из RSS, X и Telegram: обработка на русском через OpenRouter, дедупликация, тематические теги и ежедневные сводки.
- Календарь, результаты сессий, личный зачёт, Кубок конструкторов, профили пилотов и команд, опубликованные исторические сезоны.
- LIVE: тайминг, карта трассы, радио, пит-стопы и просмотр прошедших событий; Race Replay для доступных записей.
- Телеметрия: сравнение кругов, секторы, шины, гоночный темп и распределение времени кругов.
- Отчёты Гран-при с аналитикой OpenF1/FastF1 и карточки для публикации.
- Фентези: прогнозы, очки, мини-лиги и рейтинги.
- Telegram: привязка аккаунта, настройки уведомлений и защита от спойлеров.
- RaceSide Plus: платный доступ, подписка через Lava.top и управление продлением.
- «Анатомия болида»: интерактивная 3D-реконструкция с разбором 31 узла. Это учебная модель, не заводская CAD-модель.
- Админка: источники, публикации, очереди, расписания, мониторинг и аудит действий.

Доступность данных зависит от источника, сезона, сессии и прав пользователя. Наличие экрана не означает, что внешний API уже опубликовал все результаты. Web push не входит в текущую реализацию.

## Стек и устройство

Next.js 16 App Router, React 19, TypeScript, Tailwind CSS 4, shadcn/ui, Three.js; Supabase Auth/Postgres/Storage с RLS; Node.js worker и отдельный LIVE-процесс. FastF1 запускается как Python-подпроцесс.

```text
RSS / X / Telegram / Jolpica / OpenF1 / Open-Meteo / OpenRouter
                            |
                    Worker и LIVE backend
                            |
                  Supabase и серверный кэш
                            |
              Next.js: страницы, actions и API
                            |
                          Браузер
```

Ключи провайдеров и вызовы внешних API остаются на сервере. Задания планируются в базе: `cron` ставит их в очередь, `admin-job-runner` исполняет, `ops-watcher` следит за состоянием. LIVE работает отдельным долгоживущим процессом.

## Быстрый запуск

Нужны **Node.js 22+**, Corepack и **pnpm 10.11.0**. Docker необязателен для разработки. Для полной работы нужен отдельный Supabase-проект с применёнными миграциями.

```bash
corepack pnpm install --frozen-lockfile
cp .env.example .env.local
corepack pnpm dev
```

Приложение откроется на [localhost:3000](http://localhost:3000). До проверки регистрации, сохранения данных и фоновых задач настройте окружение:

| Переменные | Назначение |
| --- | --- |
| `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_APP_URL` | Адрес текущего окружения; для разработки `http://localhost:3000` |
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase URL и публичный ключ клиента |
| `SUPABASE_SERVICE_ROLE_KEY` | Только серверные операции и worker; никогда не добавлять префикс `NEXT_PUBLIC_` |
| `OPENROUTER_API_KEY` | Обработка новостей, сводки и другие AI-задачи |
| `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY` | Капча в формах авторизации |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET` | Бот и проверка webhook |
| `ADMIN_EMAILS` | Список email для серверной проверки административного доступа; действуют также проверки БД/RLS |

Остальные параметры перечислены в [.env.example](.env.example). Подключайте только нужные интеграции. Worker читает `.env`, затем `.env.local`, не заменяя уже заданные значения: не храните конфликтующие настройки в обоих файлах.

Не используйте production-базу для разработки. Запуск worker может менять данные, отправлять сообщения и расходовать кредиты внешних сервисов. Скрипты `supabase:auth` и настройки email-шаблонов меняют конфигурацию Supabase и не являются обязательным шагом локального запуска.

### База и авторизация

- Актуальная схема и изменения находятся в [supabase/migrations](supabase/migrations). На чистом проекте нужна полная цепочка; на существующем применяются только отсутствующие миграции после проверки истории.
- [05_database_schema.sql](05_database_schema.sql) является историческим документом, а не заменой миграциям. Не запускайте его поверх рабочей базы.
- В Supabase Auth настройте Site URL, разрешённые callback URL, SMTP и Turnstile для своего окружения. Рабочий callback приложения: `/auth/callback`.
- [Шаблоны писем и их установка](supabase/templates/auth/README.md) описаны отдельно. Реквизиты SMTP и Management API token в Git не хранятся.

### Worker и LIVE

Запускайте команды из корня проекта. Примеры для тестового окружения:

```bash
corepack pnpm worker:calendar
corepack pnpm worker:results
corepack pnpm worker:standings
corepack pnpm worker:rss
corepack pnpm worker:ai
```

Все готовые команды перечислены в [package.json](package.json); каталог административных заданий находится в [src/config/admin-jobs.json](src/config/admin-jobs.json).

Для локального LIVE без подключения к текущей гонке запустите во втором терминале:

```bash
corepack pnpm live:replay
```

`LIVE_INTERNAL_ORIGIN` веб-приложения должен указывать на этот процесс; локальное значение в примере окружения — `http://127.0.0.1:3002`. Режим replay является симулятором, а не текущими данными гонки. Бесплатный OpenF1 может ограничивать доступ к данным текущей сессии; это не устраняется вымышленным API-ключом.

### FastF1 и 3D-ассеты

Dockerfile устанавливает Python-окружение `/opt/fastf1` из [worker/fastf1/requirements.txt](worker/fastf1/requirements.txt). На компьютере установите эти зависимости в отдельный venv и задайте `FASTF1_PYTHON_BIN`, если нужна генерация полной аналитики. Без FastF1 часть отчёта может быть недоступна; проверяйте ошибки источников.

Готовые карты, GLB, модели болида и их манифесты входят в `public/` и нужны для работы чистого клона. Не удаляйте их как сборочный мусор. Тяжёлые исходные геоданные и рабочие Blender-файлы остаются вне Git. Инструкции: [сборка трасс](scripts/track-model-blender/README.md), [источники трасс](docs/track-model-sources-2026.md), [модель болида](docs/anatomy/w17-reference-review.md).

## Проверки

Основной набор:

```bash
corepack pnpm check:repository
corepack pnpm lint
corepack pnpm typecheck
corepack pnpm test:repository
corepack pnpm test:fantasy-scoring
corepack pnpm test:ops
corepack pnpm test:admin
corepack pnpm test:security
corepack pnpm test:live
corepack pnpm test:telemetry
corepack pnpm test:billing
corepack pnpm build
```

Запускайте `typecheck` и `build` последовательно: Next.js пересоздаёт `.next/types`. Полный перечень точечных тестов находится в `package.json`. Тесты геометрии болида выполняются отдельно и могут требовать заметного времени и памяти. Проверки внешних интеграций, реальной доставки и оплаты не заменяются unit-тестами.

[GitHub Actions](.github/workflows/quality.yml) проверяет состав репозитория, lint, типы, операционную логику, административные и security-тесты, затем собирает приложение. Секреты production для этих проверок не нужны.

## Развёртывание

[Dockerfile](Dockerfile) собирает standalone Next.js и runtime с FastF1. [docker-compose.yml](docker-compose.yml) содержит базовые сервисы; [deploy/](deploy) — серверные шаблоны. Production-конфигурация может отличаться: сетевые имена, reverse proxy, лимиты и env-файлы должны соответствовать конкретному серверу. Не заменяйте рабочий compose шаблоном вслепую.

Перед выпуском:

1. Зафиксируйте проверенный набор исходников и сделайте резервную копию конфигурации. Для DDL отдельно подготовьте резервную копию БД.
2. Сверьте миграции и примените отсутствующие до выпуска кода, который зависит от новой схемы. Сохраняйте старые данные и историю миграций.
3. Соберите один релиз с `RACESIDE_RELEASE_SHA`, обновите только затронутые сервисы. При изменениях зависимостей нужен полный rebuild runtime, а не копирование файлов в старый контейнер.
4. Проверьте `/api/health`, основные страницы, статические ассеты, LIVE и логи. Проверяйте подписку и webhook на согласованной тестовой учётной записи.
5. Сохраните предыдущий образ и план отката. При откате приложения не удаляйте данные и миграции автоматически.

Для новых оплат используется Lava.top: [настройка](docs/lava-top-setup.md), [эксплуатация подписки](docs/subscription-operations-runbook.md). Обработчики старых провайдеров оставлены для исторических платежей; это не альтернативный новый checkout. Автоматическое продление требует отдельной приёмки у провайдера.

## Документация и правила работы

Начните с [PRODUCT.md](PRODUCT.md), [DESIGN.md](DESIGN.md), [AGENTS.md](AGENTS.md) и [SKILLS.md](SKILLS.md). Навигация по регламентам и спецификациям: [docs/README.md](docs/README.md). Нумерованные документы содержат как действующие требования, так и историю решений; при противоречиях проверяйте текущий код и продуктовые документы.

В Git не должны попадать реальные env-файлы, токены, ключи, дампы БД, резервные копии, `node_modules`, `.next`, браузерные логи и рабочие каталоги генераторов. Локальные скриншоты без документированной необходимости остаются вне репозитория. В `docs/.gitignore` явно перечислены изображения, сохранённые как часть документации; для нового контрольного кадра добавьте ссылку и исключение в этом файле.

Названия `racemate` в путях и контейнерах сохранены для совместимости. Публичное имя продукта — **RaceSide**. Исторические миграции и имена не переименовываются косметически.

Чужие изображения, логотипы, геоданные и библиотеки сохраняют собственные условия использования. Атрибуция: [F1-ассеты](public/f1/ATTRIBUTION.md), [геоданные](public/geo/ATTRIBUTION.md), карточки источников в `docs/` и лицензии стороннего кода. Этот репозиторий не предоставляет права на чужие товарные знаки.
