# 3D-модели трасс RaceSide

## Назначение

Этот документ описывает, как подготовить и подключить интерактивную 3D-модель для каждой трассы сезона. Zandvoort — первый эталон цифрового двойника: он собирается в Blender из геоданных в реальных метрах. Компактные модели завершённых этапов 2026 года пока создаются отдельным генератором `scripts/generate-past-track-models.mjs`.

Для создания новой полноценной трассы агент обязан использовать подробный playbook `docs/track-model-blender-agent-playbook.md`. Этот документ сохраняет контракт общего рендерера и историю решений, а playbook задаёт полный Blender-процесс, источники и приёмку.

Модель должна показывать:

- реальную форму и направление трассы;
- заметные перепады высот;
- окружающий рельеф;
- три сектора без линии по центру полотна;
- номера поворотов, привязанные к геометрии;
- спид-трап;
- поребрики и основные зоны вылета;
- управление мышью или касанием, приближение, отдаление и возврат к исходному ракурсу;
- полноэкранный просмотр в общем диалоге для любой подключенной 3D-трассы.

Для цифровых двойников пит-лейн обязателен и строится по географическому источнику с проверкой по официальной схеме FIA. Старые компактные Canvas-модели могут оставаться без пит-лейна до переноса на Blender-пайплайн.

## Текущая реализация

Основные файлы:

- `src/components/racemate/track-model-3d-lazy.tsx` - лёгкая клиентская оболочка, Intersection Observer и отложенная загрузка чанков;
- `src/components/racemate/track-model-3d.tsx` - клиентский компонент, управление камерой, Canvas и подписи;
- `src/lib/track-model-renderer.ts` - подготовка сцены, проекция и порядок отрисовки;
- `src/lib/track-model-geometry.ts` - замыкание геометрии трассы;
- `src/lib/track-model-geometry.test.mjs` - регрессионный тест на отсутствие разрыва;
- `src/data/track-model-types.ts` - общий контракт данных, камеры и правил отрисовки;
- `src/data/track-models.ts` - реестры моделей и алиасов трасс;
- `src/data/red-bull-ring-model.ts` - исходные точки, высоты, повороты, сектора, спид-трап и сетка рельефа;
- `src/data/zandvoort-model.ts` - автоматически сгенерированные UI-метаданные Zandvoort; источником Blender-сцены этот файл не является;
- `scripts/track-model-blender/` - загрузка и фиксация геоданных, real-scale Blender-сборка, Meshopt-экспорт и валидация Zandvoort;
- `public/f1/tracks/3d/zandvoort-metadata.json` - публикационный отчёт о масштабе, длине, высотах, объектах и источниках;
- `src/data/*-model.ts` - отдельные модули моделей завершённых этапов;
- `src/data/past-track-models.test.mjs` - общая проверка замыкания, поворотов, высот, рельефа и алиасов;
- `scripts/generate-past-track-models.mjs` - воспроизводимая сборка геометрии и DEM для завершённых этапов;
- `docs/track-model-sources-2026.md` - карточка источников и качества сгенерированных моделей;
- `src/components/racemate/track-map.tsx` - выбор между 3D-моделью и обычным изображением.

`TrackModel3D` должен оставаться небольшим клиентским листом. Страница календаря и остальные контейнеры остаются Server Components, если им не нужны браузерные API.

Общий рендерер уже обобщен. Для новой трассы нужно:

1. Создать отдельный `*-model.ts` с типом `TrackModelDefinition`.
2. Передать в общий рендерер точки, рельеф, камеру и правила декора.
3. Добавить ID и алиасы в `src/data/track-models.ts` без статического импорта файла модели.
4. Добавить отдельный `import()` новой модели в `track-model-3d-lazy.tsx`.
5. Сохранить обычную картинку как fallback до прохождения проверки новой модели.

Не нужно менять архитектуру при добавлении каждой следующей трассы. Общий рендерер изменять только тогда, когда новая трасса действительно требует нового общего свойства.

Для трасс, перечисленных в генераторе, сначала обновить конфигурацию и повторно запустить:

```bash
node scripts/generate-past-track-models.mjs
```

Загрузки источников кешируются вне репозитория в `/tmp/raceside-track-model-cache`. В репозиторий попадают только небольшие готовые TypeScript-модули, а не исходные телеметрические ответы.

## Загрузка без замедления страницы

Геометрия, DEM и Canvas-рендерер не должны входить в первоначальный HTML/RSC-ответ страницы. `TrackMap` передаёт клиенту только короткий ID модели. `track-model-3d-lazy.tsx` загружает рендерер и данные трассы отдельными динамическими импортами, когда контейнер оказывается рядом с viewport, и запускает работу через `requestIdleCallback` с безопасным fallback.

Правила для новых трасс:

- не импортировать `*-model.ts` статически в `track-models.ts` или серверную страницу;
- держать реестр ID и алиасов лёгким, без точек и сетки рельефа;
- каждой трассе задавать отдельный динамический `import()`, чтобы сборщик создал отдельный чанк;
- сохранять стабильную высоту контейнера и показывать `Skeleton`, чтобы отложенная загрузка не создавала CLS;
- ошибка загрузки модели не должна ломать страницу: оставить локальный повтор загрузки;
- после сборки проверить, что исходный HTML не содержит `elevationChangeM`, `terrain` или массив точек модели.

## Контракт данных трассы

Для каждой трассы нужен набор данных следующего смысла:

```ts
type TrackModelDefinition = {
  id: string;
  aliases: readonly string[];
  data: CircuitModelData;
  terrain: CircuitTerrainData;
  camera: {
    rotationDeg: number;
    tiltDeg: number;
    scale: number;
    centerY: number;
    verticalExaggeration: number;
  };
  rendering: CircuitRenderingRules;
};
```

Точка центральной линии хранится в формате:

```ts
type CircuitModelPoint = readonly [
  progress: number,
  worldX: number,
  worldY: number,
  elevationDecimeters: number,
];
```

Требования к точкам:

- `progress` монотонно растет от `0` до `1`;
- первая точка соответствует линии старт/финиш;
- направление точек совпадает с направлением гоночного круга;
- координаты X/Y находятся в одной системе координат и одном масштабе;
- высота хранится в дециметрах, рендерер переводит ее в метры делением на 10;
- форма не должна быть вручную растянута по одной из осей;
- последняя точка должна подходить к первой без скачка положения и высоты.

Поворот хранится как номер и прогресс вдоль центральной линии. Экранные смещения допускаются только для небольшой коррекции пересечений. Основное смещение маркера от трассы должно задаваться в мировых координатах по нормали к полотну.

Действующий контракт находится в `src/data/track-model-types.ts`. Для поребриков и зон вылета в нем пока используются списки номеров поворотов. Для более точных трасс его следует расширить интервалами прогресса и стороной трассы:

```ts
type TrackSide = "left" | "right" | "both";

type CurbRange = {
  from: number;
  to: number;
  side: TrackSide;
};

type RunoffRange = {
  from: number;
  to: number;
  side: TrackSide;
  surface: "paint" | "gravel" | "grass";
};
```

Такой формат точнее привязки декора только к центру поворота. На Red Bull Ring именно слишком короткий автоматически рассчитанный диапазон сначала оставил девятый поворот без поребрика.

## Источники и подготовка данных

Для каждой трассы собрать отдельную карточку источников:

- официальная карта FIA или трассы с номерами поворотов, секторами и направлением движения;
- аэрофото или спутниковый вид для проверки формы, зон вылета и поребриков;
- геометрия центральной линии из проверенного географического источника;
- профиль высот центральной линии;
- DEM или другой источник высот для окружающего рельефа;
- официальная точка спид-трапа;
- длины первого и второго секторов либо официальные границы секторов.

Источник, лицензию, дату получения и способ преобразования нужно хранить в технической карточке ассета. Эту информацию не требуется выводить поверх модели, но она нужна для аудита и публикационного контроля.

Перед началом отрисовки открыть официальную карту и аэрофото рядом. Одного силуэта недостаточно: похожая форма может оказаться зеркальной, повернутой или иметь неправильное направление круга.

## Построение центральной линии

1. Получить упорядоченную последовательность координат по направлению круга.
2. Перенести начало последовательности на линию старт/финиш.
3. Рассчитать накопленное расстояние вдоль линии.
4. Нормализовать накопленное расстояние в `progress` от `0` до `1`.
5. Добавить высоту к каждой точке центральной линии.
6. Оставить достаточное число исходных контрольных точек в торможениях, апексах и резких изменениях уклона.
7. В рендерере уплотнить линию Catmull-Rom интерполяцией. Для Red Bull Ring используется 480 точек.
8. Ограничить интерполированную высоту диапазоном исходных высот, чтобы сплайн не создавал искусственные вершины или провалы.

После уплотнения для каждой точки рассчитывается касательная и нормаль. Нормаль используется для ширины полотна, поребриков, секторных полос и устойчивой привязки подписей.

## Обязательное замыкание трассы

Трасса является замкнутым контуром. Все слои полотна должны строиться через `createClosedLoopSegments()`:

```ts
points.map((point, index) => [
  point,
  points[(index + 1) % points.length],
]);
```

Нельзя рисовать только пары `0-1`, `1-2` и так далее до предпоследней точки. В таком варианте пропадает последний сегмент от конца массива к началу. Именно это создало разрыв между первым и десятым поворотами Red Bull Ring.

Проверка обязательна для каждого слоя:

- тень полотна;
- внешняя кромка;
- зона вылета;
- асфальт;
- секторные полосы;
- поребрики.

Регрессионный тест должен подтверждать наличие пары `last -> first` и корректную обработку пустого массива.

## Ориентация и защита от зеркальности

Сначала сделать диагностический вид строго сверху без наклона и сравнить его с официальной картой:

1. Совместить линию старт/финиш.
2. Проверить положение первого поворота относительно главной прямой.
3. Проверить последовательность трех характерных поворотов.
4. Проверить направление движения.
5. Проверить, что номера растут в правильном направлении.

В текущей проекции экранная координата X рассчитывается так:

```ts
x = viewSize / 2 - rotatedX * cameraScale * zoom;
```

Знак перед `rotatedX` исправил зеркальное отображение Red Bull Ring. Для новой трассы нельзя маскировать зеркальность перестановкой номеров поворотов или случайным вращением камеры. Сначала исправить преобразование координат, затем подобрать исходный угол камеры.

Для каждой трассы сохранить проверенный исходный ракурс в ее данных. Кнопка возврата должна восстанавливать угол, наклон и масштаб одновременно.

Исходный наклон камеры для опубликованной модели должен быть почти верхним. Для текущих моделей используется `tiltDeg: 10`: форма трассы читается сразу, а небольшой угол сохраняет ощущение рельефа. Более выраженный боковой ракурс пользователь получает вертикальным перетаскиванием.

## Высоты и рельеф

Центральная линия и рельеф могут приходить из источников с разными вертикальными датумами. Их нужно выровнять до построения сцены:

1. Сэмплировать высоту рельефа под точками трассы.
2. Вычислить остаток `trackElevation - terrainElevation` для каждой точки.
3. Вычесть средний сдвиг высот.
4. Плавно применить локальную коррекцию рельефа рядом с трассой.
5. Уменьшать влияние коррекции с расстоянием от полотна.

Это не дает трассе зависать над поверхностью или проваливаться под нее при несовпадении источников.

Рельеф строится сеткой и разбивается на треугольники. Цвет и свет должны зависеть от реальной высоты и нормали поверхности. Контурные линии помогают читать форму склона, но не должны перекрывать трассу.

Цифровые двойники Blender используют вертикальный масштаб `1.0`: один метр по высоте равен одному метру по горизонтали. Усиление `3.6` сохранено только в старом компактном Canvas-рендерере и не должно переноситься в новые GLB-сцены.

Шум DEM нельзя усиливать как настоящий рельеф. В генераторе профиль с исходным перепадом не более 18 м сглаживается циклическим окном радиуса 5, остальные трассы — окном радиуса 2. Сглаживание должно сохранять замыкание круга и не создавать новый минимум или максимум. Порог и окно проверяются общим тестом на среднюю и максимальную вторую разность профиля.

При настройке высоты учитывать:

- слишком малое значение делает рельеф плоским;
- индивидуально завышенное значение превращает малые ошибки DEM в постоянные микроскачки и ломает сравнение трасс;
- подписи минимальной и максимальной высоты должны подтверждаться данными, а не положением на экране.

Если DEM вокруг трассы содержит далёкий выброс, допустимо сжать только окружающий рельеф относительно его минимума. Так сделано для Монако с коэффициентом `terrainReliefScale: 0.48`: профиль центральной линии остаётся исходным, а высокие боковые стены сетки не закрывают модель.

Поперечный уклон бенкинга хранится в реальных градусах. Его локальную высоту нельзя повторно умножать на вертикальное усиление рельефа: иначе 19° превращаются в визуальную «стену». Знак угла должен опускать внутреннюю кромку поворота; это проверяется по знаку кривизны трассы.

## Порядок отрисовки

Слои Canvas рисуются в стабильном порядке:

1. фон и тень основания;
2. боковая юбка рельефа;
3. треугольники поверхности;
4. контурные линии;
5. тень трассы;
6. зоны вылета;
7. внешняя кромка полотна;
8. асфальт;
9. цветные кромки секторов;
10. поребрики;
11. отметки границ секторов;
12. линия старт/финиш;
13. спид-трап;
14. локально повторно отрисованные верхние полотна мостов;
15. номера поворотов.

Порядок важен. Если рисовать рельеф после трассы, часть полотна исчезнет. Если рисовать зоны вылета после номеров, они могут перекрыть маркеры.

Пит-лейна в этом списке нет.

## Мосты и близкие ветки трассы

Самопересечение центральной линии не всегда является ошибкой. Если одна ветка проходит над другой, верхний интервал задаётся через `rendering.overpasses` в координатах `progress`. Обе ветки в месте пересечения сохраняют нормальную ширину. Верхняя повторно рисуется последней теми же слоями асфальта и секторов, поэтому при виде сверху на ней нет поперечных стыков. Мост обозначают только мягкая тень, тонкая боковая грань и узкий серый бортик по краям, без белой плиты и поребриков на самом пролёте.

В Suzuka верхнее полотно перед T15 хранится как `{ from: 0.824, to: 0.86, level: true }`. Флаг `level` выравнивает высоту внутри пролёта, а короткий переход к исходному профилю происходит снаружи конструкции.

Если ветки не пересекаются в реальности, но слипаются из-за условной графической ширины, сначала измерить минимальное расстояние между несоседними точками. Общий рендерер вычисляет для каждой точки доступную половину ширины по ближайшей несоседней ветке и локально ограничивает ей все слои: тень, зоны вылета, внешнюю кромку, асфальт, секторные полосы и поребрики. Каждая сторона занимает не более 42% зазора, поэтому между соседними текстурами остаётся видимый просвет. Центральная линия при этом не сдвигается, а интервалы `overpasses` сохраняют полную ширину верхнего полотна.

Если вся модель требует более узкого полотна, можно дополнительно задать единый `trackWidthScale`; он обязан одновременно масштабировать асфальт, кромки, зоны вылета, поребрики, границы секторов, старт/финиш и спид-трап. Отдельные значения используются для Miami (`0.68`) и Montréal (`0.65`).

## Секторы без линии по центру

Центральная цветная линия ухудшала читаемость асфальта, поэтому секторы показываются несколькими согласованными средствами:

- узкими цветными полосами по обеим внешним сторонам полотна;
- короткими парными засечками снаружи трассы в начале круга и на двух границах секторов.
- для Blender-моделей точной поперечной core-полосой и более широкой полупрозрачной emissive-полосой под ней;
- подписью перехода с цветной рамкой и свечением входящего сектора.

Границы секторов рассчитываются из официальных расстояний:

```ts
firstBreak = sectorOneLength / trackLength;
secondBreak = (sectorOneLength + sectorTwoLength) / trackLength;
```

Цвет не должен быть единственным способом чтения. В легенде остаются `S1`, `S2`, `S3`, а засечки показывают точную границу на трассе.

## Номера поворотов и подписи

Номера поворотов рисуются внутри того же Canvas после проекции 3D-точки. Это устраняет рассинхронизацию с моделью при вращении и масштабировании.

Правила:

- `progress` поворота должен указывать на реальный апекс или геометрический центр поворота;
- основное удаление маркера от асфальта задается по нормали в мировых координатах;
- экранный сдвиг использовать только для небольшого разведения пересекающихся подписей;
- после поворота камеры маркер должен оставаться рядом со своей точкой;
- после приближения расстояние маркера от трассы должно масштабироваться вместе с моделью;
- текст внутри Canvas нельзя превращать в отдельные DOM-элементы без общей системы проекции;
- контейнер должен оставаться `select-none`, чтобы перетаскивание не выделяло цифры и не создавало цветные квадраты выбора текста.

На Red Bull Ring были исправлены следующие ошибки:

- номер 9 стоял на прямой между девятым и десятым поворотами, его `progress` перенесен раньше;
- номер 10 двигался отдельно от трассы, его смещение переведено в мировую нормаль;
- номера 5 и 6 визуально висели в воздухе, их экранные коррекции уменьшены;
- цифры 1-8 выделялись при перетаскивании, контейнеру добавлен запрет выделения текста.

Проверять номера нужно минимум в пяти состояниях: исходный вид, поворот влево, поворот вправо, минимальный масштаб и максимальный масштаб.

## Поребрики и зоны вылета

Положение поребриков проверяется по аэрофото, а не только по официальной линейной схеме.

Для каждого диапазона указать:

- начало и конец по `progress`;
- внутреннюю или внешнюю сторону;
- ширину;
- красно-белый шаг;
- наличие асфальтовой или гравийной зоны за поребриком.

Ошибка Red Bull Ring: стандартный радиус вокруг центра поворота не захватил всю дугу девятого поворота. Временное исправление увеличило диапазон и ширину для T9. Для остальных трасс правильнее сразу хранить интервалы и стороны в данных.

## Управление камерой

Общий `TrackModelViewer` используется обычными моделями, RaceSide LIVE и опубликованным Race Replay (через LIVE terminal). Геометрия и GLB-ассеты остаются прежними.

- На мобильном «3D» сразу открывает карту в диалоге на весь экран; после закрытия на странице остаётся схема. Встроенный 3D-просмотр на узком экране служит превью и не захватывает прокрутку страницы.
- Жесты следуют привычной схеме мобильных карт: один палец перемещает карту, щипок меняет масштаб, поворот двух пальцев вращает карту. Перемещение не упирается в прежний ограничитель ±10% кадра. Левая кнопка мыши тоже перемещает карту.
- Двумя пальцами можно одновременно приближать, поворачивать и перемещать карту. Точка между пальцами удерживается при изменении масштаба и ракурса, включая наклонённую карту и перенос от исходного центра.
- Совместное движение двух пальцев вверх увеличивает наклон, вниз возвращает вид сверху. Наклон сохраняет масштаб и направление; случайные различия в скорости пальцев не включают щипок. Явный щипок или поворот позволяет перейти обратно к свободному движению без отпускания пальцев.
- Начальный порог — 3% изменения расстояния, 3° поворота или 8px перемещения. Наклон распознаётся отдельно от совместного изменения масштаба, угла и положения. События обоих пальцев читаются вместе один раз за кадр; после отпускания одного пальца перенос продолжается от текущего положения без скачка.
- Двойное касание или двойной клик приближает выбранную область. Колесо мыши также приближает относительно курсора, до 800%.
- Правая кнопка, `Shift + drag` и сфера на десктопе меняют ракурс.
- Верхняя группа кнопок без общей подложки и рамки содержит − / + и одну кнопку «Развернуть / Свернуть карту» с соответствующей иконкой. Отдельного крестика, кнопок «Вся трасса» и «Сверху / Объём» нет. При загрузке и ошибке модели та же панель позволяет свернуть карту; масштаб недоступен до загрузки. Touch targets — 44px; учтены safe-area отступы. Переключатель 2D/3D не меняет положение между режимами: на текущем этапе, в календаре и в LIVE/Replay он остаётся снизу. Кнопка статистики в календаре сохраняет прежнее положение.
- Секторы, длина круга и профиль высот находятся у нижнего края карты; встроенный просмотр оставляет справа место для переключателя 2D/3D. Знак «≈» в высотах не показан; пояснение о приблизительных данных сохранено в подсказках.
- Клавиша Home возвращает общий вид с кадром по геометрии полотна и отступами под управление. Вытянутые трассы используют высоту портретного экрана. Наклон камеры меняется жестами, сферой на десктопе и клавиатурой.
- Центр кадра перепроецируется при каждом повороте вокруг одной точки трассы; размеры исходного кадра остаются постоянными. Это применяется к WebGL, canvas, LIVE и Replay, чтобы карта не уходила в сторону при вращении.
- Закрытие полного экрана сохраняет камеру встроенного просмотрщика. В LIVE и Replay сохраняются выбор пилота и отдельная кнопка слежения; ручное движение камеры отключает слежение, жест переноса не выбирает случайного пилота.
- Pointer capture, отмена жеста, клавиатурные стрелки, Home и − / + поддерживаются. Элементы управления не начинают перетаскивание сцены.
- Камера обновляется через requestAnimationFrame. Диалог и переходы имеют reduced-motion варианты; непрерывная инерция камеры не добавляется.

| Трасса местами исчезает | Неверный порядок слоев либо открытый контур | Стабильный порядок отрисовки и замкнутая геометрия для каждого слоя |

| `next build` конфликтует с запущенным dev-сервером | Оба процесса используют `.next` | Перед сборкой остановить `next dev`, после сборки снова запустить сервер |

| В паддоке нет моторхоумов | Временные объекты отсутствуют в кадастровых данных | Создавать отдельный event-слой по актуальному ортофото и фотографиям |

| Граница сектора теряется в общем ракурсе | Одна узкая линия слишком мала | Добавлять core-полосу, emissive halo, цветную подпись и легенду |

## Процесс добавления одной трассы

### Сбор данных

- определить стабильный ID и алиасы названия;
- сохранить ссылки и метаданные источников;
- получить центральную линию в направлении круга;
- отметить старт/финиш, повороты, сектора и спид-трап;
- получить профиль высот и сетку рельефа;
- отметить интервалы поребриков и зон вылета.

### Подготовка модели

- привести координаты к одной системе;
- вычислить `progress` по реальной длине линии;
- проверить единицы высоты;
- выровнять высоты трассы и рельефа;
- добавить данные в отдельный файл трассы;
- зарегистрировать модель по ID, не только по отображаемому названию.

### Настройка вида

- сначала сравнить ортографический вид сверху;
- подтвердить отсутствие зеркальности;
- подобрать исходный угол и наклон;
- для Blender-модели подтвердить вертикальный масштаб `1.0`;
- убедиться, что трасса помещается в сцену на мобильном и десктопе;
- проверить максимальное приближение 800%.

### Разметка

- поставить повороты по апексам;
- развести только конфликтующие номера;
- добавить секторные кромки и засечки;
- отметить спид-трап;
- добавить поребрики и зоны вылета по аэрофото;
- добавить и сверить пит-лейн, fast lane и точки въезда/выезда по схеме FIA.

### Приемка

- сравнить силуэт и направление с официальной картой;
- проверить разрыв на линии старт/финиш крупным планом при 800%;
- проверить заметность реальных перепадов;
- повернуть модель в обе стороны и изменить наклон;
- проверить каждую цифру на минимальном и максимальном масштабе;
- проверить, что сектора читаются без центральной линии;
- проверить поребрики с обеих сторон каждого поворота;
- проверить светлую и темную темы;
- проверить 375, 768, 1024 и 1440 px;
- проверить мышь, touch и клавиатуру;
- проверить, что модель загружается отдельным чанком только рядом с viewport;
- сравнить размер первоначального HTML/RSC до и после подключения модели;
- проверить, что обычная карта остается fallback до публикации модели.

Затем открыть страницу этапа в локальном браузере и проверить модель в реальном размере. Контрольные страницы:

Предупреждение гидратации, связанное с `data-theme` в `src/app/layout.tsx`, является отдельной известной проблемой проекта. Его не следует принимать за ошибку 3D-модели, но перед массовой публикацией лучше исправить отдельно.

## Критерии готовности трассы

Модель можно включать вместо картинки, когда выполнены все условия:

- форма и направление подтверждены по двум источникам;
- модель не зеркальная;
- замыкание на старт/финише не видно при 800% масштабе;
- перепады высот читаются в исходном ракурсе и не выглядят искусственно;
- рельеф не пересекает полотно;
- все номера находятся у своих поворотов при любом доступном ракурсе;
- сектора читаются по внешним кромкам и засечкам;
- спид-трап стоит в подтвержденной точке;
- поребрики и зоны вылета проверены по аэрофото;
- пит-лейн и его точки въезда/выезда совпадают с официальной схемой;
- управление мышью, touch, клавиатурой, зум, возврат и полноэкранный режим работают;
- нет выделения текста, наложений и обрезанных подписей;
- легенда секторов, профиль высот и оба значения уклона полностью помещаются в контейнер;
- модель прошла desktop, mobile, light и dark проверки;
- геометрия и рельеф отсутствуют в первоначальном HTML/RSC и загружаются отложенно;
- lint, typecheck, тест геометрии и build проходят.

## Albert Park 2026

`albert-park` переведён со старой схемы на текстурированный Blender GLB. Модель использует текущие границы гоночного полотна организатора, FIA 2026 и Vicmap AHD; OSM задаёт главную прямую, постоянный пит-фронт, топологию и инфраструктуру. Оси трассы и пит-лейна разделены; в общей зоне стыков используется согласованный профиль высот. Пайплайн: `pnpm track:3d:build albert-park`, `pnpm track:3d:validate albert-park`. Компактный модуль данных и GLB остаются ленивыми, обычная карта и preview — доступными fallback. Генератор прошлых Canvas-моделей пропускает этот ID. Подробнее: [источники](track-model-albert-park-source-card.md), [приёмка](track-model-albert-park-build-report.md).
